# Как мы работаем

Над порталом работают несколько человек, и у каждого свои ИИ-агенты. Боевой стенд один: сайт ebl.su, бот в чате лиги
и база в Supabase. Если в `main` попадёт непроверенная правка, вся лига сразу увидит поломку. Поэтому с 27.09.2026 мы
работаем по схеме ниже. Для людей и агентов она одинаковая.

## Коротко — пять правил

1. **В `main` лежит то, что можно выложить.** Напрямую в `main` не коммитим и не пушим. GitHub это и не даст: ветка защищена.
2. **Каждая задача — своя ветка и свой pull request (PR).** Проверки зелёные → PR сливаем → выкладываем.
3. **Выкладываем только скриптами** `scripts/deploy.sh` (сайт) и `scripts/deploy-backend.sh` (база и функции).
   Запускаем их только из свежего `main`. Скрипты сами гоняют все тесты и без зелёных ничего не выкладывают.
4. **Перед выкладкой пишем в чат разработки «выкладываю …»**, чтобы две выкладки не наложились друг на друга.
5. **Новое поведение — новый тест.** Если сломанное не ловится тестами, оно сломается снова.

## Рабочее место — настроить один раз

Нужны `git`, [GitHub CLI](https://cli.github.com) `gh`, [Supabase CLI](https://supabase.com/docs/guides/cli), Docker Desktop,
Python 3, Google Chrome (сайт тестируется в настоящем Chrome) и — чтобы выкладывать сайт — [Yandex Cloud CLI](https://yandex.cloud/ru/docs/cli/quickstart) `yc`.

```bash
gh auth login                                     # под своим аккаунтом GitHub
gh repo clone alekkan/ebl && cd ebl
pip3 install playwright                           # браузерные тесты сайта (Chrome берётся установленный, браузеры playwright не нужны)
supabase login
supabase link --project-ref yeerkfdgmhcmvdqzaoio  # нужен доступ к проекту в Supabase — его выдаёт Леха
curl -sSL https://storage.yandexcloud.net/yandexcloud-yc/install.sh | bash   # yc — для выкладки сайта
~/yandex-cloud/bin/yc init                        # вход через Яндекс ID, каталог ebl; доступ (роль storage.editor) выдаёт Леха
```

Сайт лежит в хранилище Яндекса, `scripts/deploy.sh` заливает его через `yc` под твоим входом — отдельных ключей нет.
Подробности про хостинг и откат — в [operations.md](operations.md#домен-eblsu).

Локальный стенд — копия боевого на твоём компьютере в Docker. Все тесты гоняются на нём, боевую базу они не трогают.

```bash
supabase start
supabase db reset                                 # схема + входящий остаток из seed.sql
docker exec supabase_db_ebl psql -U postgres -c "select cron.unschedule(jobname) from cron.job"   # иначе локальный cron дёргает боевые функции
docker exec supabase_db_ebl psql -U postgres -c "update settings set value = '\"http://supabase_kong_ebl:8000/functions/v1\"' where key = 'functions_url'"
cp -n supabase/functions/.env.example supabase/functions/.env                                       # фейковые токены, только для тестов
supabase functions serve --env-file supabase/functions/.env                                         # в отдельном терминале, пусть работает
scripts/check.sh                                  # должно закончиться «Все проверки пройдены.»
```

В `.env` — фейковые токены и адреса заглушки внешних сервисов (Telegram, геокодер, npm-CDN): тесты поднимают её сами и
в интернет не ходят. Если `.env` у тебя старый, допиши недостающие строки из `.env.example` и перезапусти
`supabase functions serve` — иначе тесты остановятся и скажут, чего не хватает.

`prototype/config.js` смотрит в боевой Supabase: тест сайта сам подменяет его на локальный. Если хочешь потыкать сайт
руками на локальном стенде, временно впиши адрес `http://127.0.0.1:54321` и ключ из `supabase status`, но **не коммить это**.

## Одна задача от начала до конца

### 1. Начни со свежего `main`

```bash
git switch main && git pull
```

Если берёшься за крупное (бот, правила очков, схема базы), напиши в чат разработки, чем занимаешься. Два человека
в одном файле потом будут долго распутывать конфликты.

### 2. Заведи ветку

```bash
git switch -c fix/rejected-bath-on-map
```

Имя ветки начинается с типа задачи:

| Префикс | Когда |
|---|---|
| `feat/` | новое: экран, кнопка, возможность бота |
| `fix/` | починка |
| `docs/` | только документация |
| `ops/` | скрипты, выкладка, тесты, инфраструктура |
| `data/` | правка данных в боевой базе (см. «Данные на бою») |

Одна задача — одна ветка. Не смешивай в одном PR починку бота и новую вёрстку: такой PR трудно проверить и трудно откатить.

### 3. Внеси изменения и добавь тест

Где что лежит — в [AGENTS.md](../AGENTS.md), подробности — в `docs/`. Куда писать тест:

| Меняешь | Тест |
|---|---|
| схему, права, RPC, триггеры, `recompute`, `scoring.js` | `tests/test_backend.py` |
| разбор постов и ответы бота | `tests/test_bot.py` |
| сайт (всё видимое, сценарии гостя, участника, Комиссии, телефон) | `tests/test_site.py` — новый сценарий |

Меняешь бота — пройди ещё и ручной сценарий из [docs/bot.md](bot.md#что-проверить-руками-после-изменений) в тестовой группе.

### 4. Прогони проверки

```bash
scripts/check.sh
```

Не оборачивай его в `| tail` без `set -o pipefail`: труба отдаёт код возврата `tail`, и провал проверок выглядит как успех
(так однажды открылся PR с упавшим тестом). Скрипт гоняет три набора тестов:

- бэкенд: вход, права, поход → модерация → очки;
- бот: разбор постов;
- сайт в Chrome: за гостя, участника и Комиссию, на телефоне и в режиме витрины.

Любая ошибка в консоли браузера, упавший сценарий или вылезшая за экран вёрстка — провал. Логи лежат в `/tmp/ebl-<набор>.log`.

Упал чужой тест? Не удаляй и не ослабляй его, чтобы стало зелёным: он ловит то, что уже однажды ломалось. Разберись или
спроси автора.

### 5. Закоммить

Коммиты пишем по-русски. Первая строка — что изменилось, понятными словами. Ниже — зачем.

```bash
git add -A
git commit -m "Отклонённая новая баня пропадает с карты

Комиссия отклонила поход, а заведённая под него баня висела на карте и на Столе Комиссии."
```

Мелких коммитов в ветке может быть сколько угодно: при слиянии они схлопнутся в один.

### 6. Отправь и открой PR

```bash
git push -u origin HEAD
gh pr create --fill          # или без --fill — спросит заголовок и описание
```

Описание PR подставится из шаблона `.github/pull_request_template.md`. Заполни его: что и зачем, как проверил, что
выкладывать. PR видят все, в нём же обсуждаем правку.

**Второй человек смотрит PR обязательно, если PR:**

- меняет правила очков (`scoring.js`) — сошлись на решение Комиссии;
- трогает права доступа (RLS, `grant`, что видит гость);
- удаляет или переименовывает что-то в схеме базы;
- правит данные на бою.

Позвать: `gh pr edit --add-reviewer <логин>`. Остальное автор может слить сам, когда проверки зелёные.

### 7. Слей PR

```bash
gh pr merge --squash --delete-branch
```

Если GitHub пишет, что есть конфликт, смотри раздел «Конфликты» ниже.

### 8. Выложи и проверь на бою

См. раздел «Выкладка». После выкладки проверь своё изменение на ebl.su или в чате. Если в PR нужно было выкладывать
что-то вручную (данные, настройки), отметь в PR, что сделано.

## Выкладка

| Что поменял | Команда |
|---|---|
| Сайт (`prototype/`) | `scripts/deploy.sh` — в хранилище Яндекса и в резерв на GitHub Pages |
| Миграции (`supabase/migrations/`) | `scripts/deploy-backend.sh` — накатит новые миграции, выложит функции, пересчитает таблицу |
| Одну функцию (`tg-bot`, `tg-login`, `bath-location`, `sync-avatars`) | `scripts/deploy-backend.sh tg-bot` |
| Правила очков (`_shared/scoring.js`) | `scripts/deploy-backend.sh recompute` — выложит движок и сразу пересчитает таблицу |
| Общий код функций (`_shared/geo.ts`, `place.ts`, `greetings.ts`…) | `scripts/deploy-backend.sh` без аргументов — все функции |
| И сайт, и бэкенд | сначала `scripts/deploy-backend.sh`, потом `scripts/deploy.sh` |

**Порядок:**

1. `git switch main && git pull`.
2. В чат разработки: «выкладываю бота» / «выкладываю сайт».
3. Запусти скрипт. Он сам проверит, что ты на `main`, рабочая копия чистая, `main` совпадает с GitHub, а `scripts/check.sh` зелёный.
   Если хоть что-то не так, скрипт остановится и ничего не выложит.
4. Проверь результат:
   - сайт обновляется сразу (страница в Яндексе без кэша); если видишь старое, обнови страницу;
   - бот: отправь пост в тестовой группе или `curl -s "https://yeerkfdgmhcmvdqzaoio.supabase.co/functions/v1/tg-bot?diag=1"`;
   - пересчёт печатает `{"ok":true,"players":…,"currentWeek":…}`.

**Совместимость.** Миграции накатываются раньше, чем выложен новый сайт, поэтому текущий сайт с новой схемой ломаться
не должен. Добавлять столбцы и функции можно смело. Переименование и удаление делаем в два захода:

1. добавить новое и перевести на него код;
2. следующим PR убрать старое.

**`SKIP_CHECKS=1 scripts/deploy.sh`** выкладывает без тестов. Это только на крайний случай: бой лежит, а тесты сломаны
по причине, не связанной с правкой. Напиши в чат, почему так, а тесты почини следующим PR.

**Руками не выкладываем.** Никаких `supabase functions deploy`, `supabase db push` и пушей в `gh-pages` в обход скриптов.
Так уже уезжали изменения без тестов.

## Конфликты и параллельная работа

Конфликт появляется, когда два PR поменяли одни и те же строки. Первый PR сливается спокойно, второй GitHub помечает
как `CONFLICTING`. Что делать со вторым:

```bash
git switch <твоя-ветка>
git fetch origin && git merge origin/main
# открой файлы с <<<<<<< и оставь нужное из обеих версий (обычно нужны обе правки)
git add <файлы> && git commit
scripts/check.sh             # после разрешения конфликта — обязательно
git push
```

Пример (27.09.2026): PR #2 и PR #3 оба меняли строку карточки бота. В итоговой версии остались обе правки: статус
«Ушло в Комиссию ✅», приветствие Женька строкой ниже и предупреждение о повторе.

Пушить с `--force` можно только в свою ветку, которую никто, кроме тебя, не трогает. В `main` и в чужие ветки — никогда.

## Данные на бою

- **Походы, бани, привязки аккаунтов.** Если можно сделать через сайт (лента у Комиссии, Стол Комиссии, правка заявки) или кнопками
  бота, делай там, а не SQL.
- **Если нужен SQL** (переименовать, перепривязать, слить дубли):
  1. заведи ветку `data/…`;
  2. положи файл `scripts/datafix_<ГГГГ-ММ-ДД>.sql` с комментарием, кто попросил и зачем, и рядом `…_backup.sql` —
     как вернуть было;
  3. открой PR, и пусть второй посмотрит;
  4. после слияния:
     ```bash
     supabase db query --linked -f scripts/datafix_….sql
     scripts/deploy-backend.sh recompute
     ```
- **Удаляем только по явным id**, предварительно посмотрев `select`-ом, что именно удаляется. С W39 в журнале
  настоящие походы: удаление «по дате» снесёт их вместе с очками.
- **Схему меняем только новыми миграциями** `supabase/migrations/<ГГГГММДДЧЧММСС>_<что>.sql`. Старые не правим:
  на бою они уже применены, и правка ничего не изменит, только рассинхронизирует локальный стенд с боем.
  В новых таблицах включай RLS и выдавай права явно (подробнее — в AGENTS.md).
- **Таблицу Виктора** (Google Sheets) портал только читает. Ничего в неё не пишем.
- **Правила очков** меняем только по решению Комиссии. Дату решения пишем в комментарии в `scoring.js` и в
  [docs/scoring.md](scoring.md), поведение закрываем тестом.

## Если сломалось на бою

1. Напиши в чат разработки, что видишь и с какого времени.
2. **Откат — тоже через PR**, так быстрее всего и надёжнее:
   ```bash
   git switch main && git pull && git switch -c fix/revert-<что>
   git revert <коммит из main>          # у слитого PR он один — squash
   git push -u origin HEAD && gh pr create --fill && gh pr merge --squash --delete-branch
   scripts/deploy.sh                    # или scripts/deploy-backend.sh <функция>
   ```
3. **Миграцию не откатываем удалением файла.** Пишем новую миграцию, которая возвращает как было.
4. Где смотреть:
   - логи функций — дашборд Supabase → Edge Functions → функция → Logs;
   - состояние бота — `tg-bot?diag=1`;
   - сайт — консоль браузера.
5. Починил — добавь тест, который ловит эту поломку. Так появились проверки на `visit_points.id` и на аватарку-точку на телефоне.

## Чего не делаем никогда

- Не коммитим и не пушим в `main`, не делаем `--force` в `main`.
- Не выкладываем руками в обход `deploy.sh` и `deploy-backend.sh`.
- Не правим старые миграции.
- Не пишем в таблицу Виктора.
- Не удаляем данные на бою по дате или условию без явных id.
- Не храним и не пересылаем секреты: ни в коде, ни в чате, ни в PR.
- Не выдаём доступы. Доступы выдаёт только Леха.
- Не открываем гостям журнал походов, даты и компании.

## Для ИИ-агентов

Всё выше относится и к тебе. Дополнительно:

- **Перед работой** прочитай [AGENTS.md](../AGENTS.md), этот документ и тот файл из `docs/`, который касается задачи.
- **Начинай со свежего `main`** в своей ветке. Никогда не коммить в `main` и не переписывай чужие ветки.
- **Выкладывай, только когда твой человек попросил или согласился.** Перед выкладкой скажи ему, что выкладываешь
  (он передаст «выкладываю» в чат разработки).
- **Данные на бою** меняй только по явной просьбе человека и сначала покажи, что изменится (`select`). Удаление — только по id.
- **Секреты не проси и не печатай.** Токен бота владелец ставит сам.
- **Тесты не ослабляй**, чтобы стало зелёным. Если тест мешает, объясни человеку почему.
- **Описание PR** заполняй по шаблону: что и зачем, как проверил, что выкладывать. Проверку описывай честно: что прогнал,
  что не прогнал.
- **Коммиты, PR, комментарии и тексты интерфейса пиши по-русски**, коротко, на «ты».

## Защита `main`

На GitHub включена защита ветки `main`:

- изменения попадают туда только через pull request, даже у владельца;
- `--force` и удаление ветки запрещены.

Посмотреть: `gh api repos/alekkan/ebl/branches/main/protection`. Ветка `gh-pages` — просто сборка сайта (резерв на GitHub
Pages). Её перезаписывает `deploy.sh`, защита на неё не распространяется.
